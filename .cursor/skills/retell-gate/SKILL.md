# 复述门 Skill

你不是在写 changelog，也不是在夸这段代码。你是在把一次改动从「能跑」变成「作者能讲」。

硬规则：你自己讲不清的函数，必须写进「不确定」。不准用流畅的废话填过去。不确定非空 = 这份复述的裁决是「不准合」。

## 何时触发

用户出现下面任一意图，就走这套流程，不要先问一堆无关问题：

| 用户怎么说 | 模式 |
| --- | --- |
| 「分析最新提交」「复述 HEAD」「刚交的这单看不懂」 | `HEAD` |
| 「分析 `abc1234`」「复述这个 hash」「上周那次 hotfix 是啥」 | 指定 hash |
| 「给这个 commit 写 PR 说明」「复述门文档」 | 按上面两者之一，输出必须能直接贴进 PR |
| 「这段 AI 代码我看不懂」「黑盒」「90 秒复述」 | 默认 `HEAD`；工作区还有未提交改动时先问清看提交还是看工作区 |

没给 hash、也没说「最新」：默认 `HEAD`。一句话确认目标后立刻开干。

可叠加的实际场景（自动识别，不必用户会用术语）：

- **AI 刚写完还没 commit**：分析工作区 diff（`git diff` + `git diff --cached`），目标写成 `WORKTREE`。
- **一个 PR / 一段历史**：用户给了两个 hash、分支名或 `main...HEAD`，按 range 分析，合并成一份复述，按关注点切，不要按 commit 流水账。
- **出事了要对着某次提交排**：仍走完整模板，但「排查」和「回滚」两节加长，90 秒复述改成「我现在怀疑什么」。

一次只分析一个目标。用户同时丢三个 hash，拆成三份文档，不要揉成一锅。

## 禁止做的事

- 用「优化了」「重构了」「完善了」「提升了可维护性」当行为变化。
- 只读 `git show --stat` 就开写。没读关键函数上下文，等于没看。
- 把 AI 自己写的测试当「已证明正确」。
- 替作者编造动机。commit message 只是线索，以代码为准。
- 为了好看而省略不确定的地方。
- 输出纯聊天、不落盘。必须写出 Markdown 文件。
- 在复述里教用户「可以让 AI 再解释一遍」——解释不是理解。

## 工作流

### 1. 锁定目标

在仓库根目录执行，先确认你在对的 repo：

```bash
git rev-parse --show-toplevel
git status -sb
```

解析目标：

```bash
# 最新提交
git rev-parse HEAD
git log -1 --format=fuller HEAD

# 指定 hash（短号也行）
git rev-parse --verify <hash>^{commit}
git log -1 --format=fuller <hash>
```

hash 不存在、指向 tag/tree 而不是 commit：停，告诉用户，不要猜最近的相似 hash。

记录：完整 SHA、短号、作者、日期、原 commit message、父 commit。合并提交要说清楚，并声明你分析的是对第一父的 diff（`git show -m --first-parent`），除非用户要看进来的分支。

### 2. 取证（写之前必须做完）

按这个顺序拿证据，缺一步就补：

```bash
git show --stat --format=fuller <hash>
git show --name-status <hash>
git show --format= -- <hash>          # 完整 diff；太大就先 --stat 再按文件 git show <hash> -- path
```

然后对每个「有行为含义」的文件：

1. 打开 diff 里改动的函数/组件/类型的**改后全文**，不要只看 hunk。
2. 找到调用方和被调用方。改了函数签名，必须看至少一处调用。
3. 看测试：哪些断言是新的、期望值是什么、有没有只测快乐路径。
4. 看配置/SQL/权限/feature flag/环境变量——这些经常比业务代码更致命。
5. 忽略 lockfile、生成物、格式化噪音，除非它们改变了运行时依赖版本。

diff 超过约 400 行有效业务代码，或一个提交里明显有多个关注点：在文档开头写「超标，建议拆」，但仍按关注点写完，不要偷懒只写第一段。

### 3. 按关注点切开，不要按文件流水账

人脑一次只能装一个行为变化。把 diff 收成 1–4 个关注点。典型切法：

- 用户可感知的行为（多了/少了什么）
- 数据或协议变化（字段、错误形状、兼容）
- 控制面（权限、开关、调度、重试）
- 纯移动文件/重命名：能一行带过就一行，不要假装深刻

每个关注点必须能用一句话回答：「系统因此多了或少了什么。」答不出来，这个关注点还没成立，继续读。

### 4. 每个关注点写清四件事

对每个关注点写：

1. **做了什么**：可观察行为，带入口（路由、CLI、job、函数名）。
2. **为什么这样改**：用代码里的约束说话（要过某条测试、要兼容旧数据、要修某类失败）。没有证据就写「作者没留下原因，从代码能看出的是…」。不准脑补产品故事。
3. **数据怎么流**：入口 → 分叉 → 出口。点名关键函数。失败时写不写库、回不回滚、返什么错。
4. **三个失败模式**：外部依赖挂了、脏输入、重入/部分失败。写不出三个，说明你还在读主路径小说。

### 5. 难懂代码单独拎出来

符合任一条，就进「难懂清单」，用醒目标注，禁止埋在段落里：

- 超过一个抽象层才能看懂输入输出
- 隐式状态：全局、单例、闭包里的可变缓存、`Date.now()`、时区
- 非显而易见的控制流：正则、位运算、巧妙短路、自定义调度、手动状态机
- 新发明的 `Base*` / `*Service` / `utils` / wrapper，而仓库里没有第二次使用
- 你读了两遍仍不能在纸上画出分支
- 错误被吞：空 `catch`、`|| []`、`?? 0`、返回 `null` 当成功

每一条难懂项必须包含：

- 文件路径 + 符号名
- **为什么难**（不是「比较复杂」）
- **你现在的理解**（允许写「我不确定」）
- **删到能重建的建议**：缩小、内联、或作者手写一遍

你自己都标了不确定的符号，后面不准再写成「已理解」。

### 6. 风险与排查

按这 8 个点猎，有就写，没有写「本 diff 未见」，不要每条都编故事：

1. 错误有没有被吞
2. 边界：空、超大、超时、重入、部分失败
3. 隐式耦合：环境变量、时间、随机、进程内缓存
4. 并发与幂等
5. 数据与兼容：旧数据、旧客户端
6. 权限与信任边界
7. 可观测性：失败时能不能从日志重建现场
8. 回滚：能不能安全撤

「出问题怎么查」必须具体到这个 diff，禁止通用教程式：

- 先看哪条日志 / 哪个指标 / 哪张表
- 用什么命令或请求复现主路径和失败路径
- 模型和现场对不上时，第一处该对的分叉在哪
- 回滚步骤：`git revert <hash>` 够不够，有没有迁移要倒

默认动作仍然是：先重建状态机，再生成补丁。复述文档里不要写「把报错丢给 AI」。

### 7. 90 秒复述

用作者能对着人讲的口吻，不超过 8 句。必须覆盖：

1. 系统多了或少了什么
2. 数据从哪进、从哪出
3. 最危险的一个失败
4. 怎么证明它对（具体命令或那条断言）
5. 还有没有你讲不清的地方（没有就明确说「没有」）

写完后自己计时：正常语速超过 90 秒就删句子，不要删风险。

### 8. 复述门裁决

过门条件（全满足才是「可以合」）：

- 行为变化不是空话
- 数据流能画到分叉
- 至少三个失败模式
- 「不确定」为空
- 指出了验证方式
- 核心断言看起来像人定的，或你能指出哪几条期望值是有意义的

否则写 **不准合**，并列原因。原因要能让作者回去做事：读哪个函数、删哪层、拆哪个关注点。

有债但能讲清：写「勉强可合，但有债」。

### 9. 落盘

默认路径：

```
docs/retell/YYYY-MM-DD-<shortsha>.md
```

工作区 diff 用 `docs/retell/YYYY-MM-DD-worktree.md`。用户指定了路径，听用户的。

同时做两件事：

1. 把完整 Markdown 写入该文件。
2. 在对话里贴 **90 秒复述 + 裁决 + 文档路径**。不要把整篇再贴一遍，除非用户要。

日期用仓库里该 commit 的日期；工作区用今天。时区跟 commit 走。

## 质量自检（写完对照，失败就改文档）

- [ ] 把 90 秒复述读出声，像人话，不像发布说明
- [ ] 每个关注点都能指出入口符号
- [ ] 难懂项都有路径，没有「相关逻辑比较绕」
- [ ] 风险表没有全空，也没有八行都在说「需进一步观察」
- [ ] 不确定栏与正文不互相打架
- [ ] 文档能直接当 PR 正文：上面是复述，下面是风险，评审不用再猜你看没看

## 和手册其它页的关系

- 生成前应先走任务卡（`/brief`）。复述门不补写任务卡，只陈述既成事实。
- 裁决标准对齐 `/gate`：不确定非空 = 不准合。
- 风险猎点对齐 `/review` 的八件事。
- 排查步骤对齐 `/debug`：先重建模型。
- 不要在复述里给黑盒指数打分，除非用户同时要；要打就另开 `/score` 的口径，不要发明第三套分数。
